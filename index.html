The core idea

Treat Codex like a skilled technician working from a controlled drawing package.

You provide the required behavior, observed condition, constraints, and acceptance test. Codex can inspect the system, trace how it works, make changes, and run tests. You still verify the result.

What Codex needs from you

1. Goal: what the system must do.

2. Current condition: what it does now.

3. Constraints: what must not be disturbed.

4. Verification: how success will be proven.

You do not need to tell Codex how to write every line. Give it the engineering problem and the operating limits.

Working with Codex

The engineering loop

For important work, follow the same sequence every time.

  1. 1
    Requirement

    Define the desired result and constraints.

  2. 2
    Inspect

    Read the existing implementation first.

  3. 3
    Trace / Reproduce

    Follow the data path or reproduce the fault.

  4. 4
    Plan

    Find the smallest clean integration point.

  5. 5
    Modify

    Make the bounded change.

  6. 6
    Test

    Run appropriate checks.

  7. 7
    Review the diff

    Inspect exactly what changed.

  8. 8
    Verify

    Compare the result to the original requirement.

Default instruction:

“Inspect the existing system first. Trace the relevant path, identify the best integration point or root cause, make the smallest clean change, run the appropriate tests, and report what changed and how you verified it.”

Troubleshooting

Fault-finding procedure

1Define expected behavior.
State exactly what should happen.
2Record observed behavior.
State what actually happens, including errors or logs.
3Reproduce the fault.
Make the failure repeatable when possible.
4Trace the path.
Follow input → processing → output and find the first divergence.
5Identify root cause.
Do not patch the visible symptom if the fault is upstream.
6Correct and verify.
Make the smallest repair, test it, then check for regressions.
Reference

Starter glossary

Literal definition first. Engineering analogy second.

Repository (repo)

What it is

The complete version-controlled collection of files that make up a software project.

Engineering parallel

The controlled drawing and documentation package for the complete system.

File

What it is

A single stored unit of source code, configuration, documentation, or other project data.

Engineering parallel

One sheet or document inside the drawing package.

Function

What it is

A named block of code that performs an operation. It may receive inputs and return an output.

Engineering parallel

A functional circuit block with a defined job and interface.

Where the analogy breaks

Functions can call other functions, modify shared state, and behave in ways with no direct physical equivalent.

Module

What it is

A logical unit that groups related code and exposes useful behavior.

Engineering parallel

A subsystem or assembly made from several cooperating functional blocks.

Dependency

What it is

External code, a library, service, or component another part of the system requires.

Engineering parallel

A supplied subsystem or component required by your design.

API

What it is

An Application Programming Interface defines how software components communicate: requests, accepted inputs, and returned results.

Engineering parallel

A defined electrical or communications interface with specified signals and expected behavior.

Optional 40K mnemonic

A standardized interface between ship systems: internal construction can differ as long as both systems obey the interface.

Server

What it is

A program or machine that listens for requests and provides data or services to clients.

Engineering parallel

A shared subsystem providing a defined service to connected systems.

Database

What it is

A system for storing, organizing, retrieving, and changing persistent structured information.

Engineering parallel

A controlled records store queried by other systems.

Commit

What it is

A recorded Git revision containing a specific set of project changes and a message describing them.

Engineering parallel

A controlled revision checkpoint in the engineering record.

Diff

What it is

A line-by-line comparison showing what was added, removed, or changed between versions.

Engineering parallel

Redlines or an engineering change comparison between revisions.

[What should happen]

OBSERVED BEHAVIOR
[What actually happens]

EVIDENCE
[Errors, logs, screenshots, measurements, reproduction steps]

CONSTRAINTS
[What must not change]

Before modifying anything, reproduce the problem if possible.
Trace the relevant path from input to output.
Identify where behavior first diverges from expectation.
Find the root cause rather than patching the symptom.

Make the smallest clean correction, run the appropriate tests,
and explain how the result was verified.

Explain an Existing System

Do not change anything yet.

Inspect how [feature/system] currently works.

Trace it from input to output and identify:
- the main files involved
- the important functions/modules
- external dependencies
- where data enters
- where decisions are made
- where data leaves
- relevant tests

Explain the architecture in plain technical language.
Call out anything uncertain rather than guessing.

Add a Capability

GOAL
[Capability to add]

REQUIRED BEHAVIOR
[Inputs, outputs, and important cases]

CONSTRAINTS
[Compatibility, interfaces, files, dependencies, performance]

DONE WHEN
[Acceptance criteria]

First inspect the existing architecture and identify the cleanest
place for this capability. Reuse existing patterns where practical.

Then implement the smallest maintainable change, add or update tests,
run verification, and summarize the final diff and any remaining risks.
Verification

Codex is part of the test process, not the test instrument.

Codex result→Review diff→Run tests→Exercise real behavior→Confirmed

For engineering facts, calculations, component specifications, standards, or safety-critical work, verify against authoritative documentation and appropriate real-world tests.
