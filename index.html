The circuit model

Translate familiar engineering concepts into software terms without losing the important distinctions.

01
Drawing package→Repository

The complete, version-controlled collection of files that makes up a project.

02
Functional block→Function / module

A named unit of code with a defined job and interface.

03
Signal→Data

Information moving between parts of a system or across an interface.

04
Test fixture→Automated test

A repeatable check that compares actual behavior with expected behavior.

!
The most important habit: inspect before you modify.

State the goal, current condition, constraints, and acceptance test. Then let the existing system show you where the change belongs.

engineering-loop.exe02 / 05
Working with Codex

The engineering loop

For important work, use the same controlled sequence every time. Each pass reduces ambiguity before the next one begins.

  1. 01Requirement

    Define the desired result and constraints.

  2. 02Inspect

    Read the existing implementation first.

  3. 03Trace / reproduce

    Follow the data path or make the fault repeatable.

  4. 04Plan

    Find the smallest clean integration point.

  5. 05Modify

    Make the bounded change.

  6. 06Test

    Run checks proportional to the risk.

  7. 07Review the diff

    Inspect exactly what changed.

  8. 08Verify

    Compare the result with the original requirement.

When something is wrong

Fault-finding procedure

01Define expected behavior. State exactly what should happen.
02Record observed behavior. Include errors, logs, and reproduction steps.
03Trace the path. Follow input → processing → output and find the first divergence.
04Correct and verify. Fix the root cause, then check for regressions.
reference-bay.exe03 / 05
Reference bay

Decode the vocabulary

Literal definition first. Engineering parallel second. Where an analogy breaks, say so.

Repository repo+

What it is

The complete version-controlled collection of files that makes up a software project.

Engineering parallel

The controlled drawing and documentation package for the complete system.

File sheet+

What it is

A single stored unit of source code, configuration, documentation, or project data.

Engineering parallel

One sheet or document inside the drawing package.

Function block+

What it is

A named block of code that performs an operation. It may receive inputs and return an output.

Engineering parallel

A functional circuit block with a defined job and interface.

Module assembly+

What it is

A logical unit that groups related code and exposes useful behavior.

Engineering parallel

A subsystem or assembly made from several cooperating blocks.

Dependency library+

What it is

External code, a library, service, or component another part of the system requires.

Engineering parallel

A supplied subsystem required by the design.

API interface+

What it is

An interface defining how software components communicate: accepted inputs and returned results.

Engineering parallel

A defined communications interface with specified signals and expected behavior.

Database records+

What it is

A system for storing, organizing, retrieving, and changing persistent structured information.

Engineering parallel

A controlled records store queried by other systems.

Commit checkpoint+

What it is

A recorded Git revision containing a specific set of project changes and a message.

Engineering parallel

A controlled revision checkpoint in the engineering record.

Diff redline+

What it is

A line-by-line comparison showing what was added, removed, or changed between versions.

Engineering parallel

Redlines or an engineering change comparison between revisions.

Server service+

What it is

A program or machine that listens for requests and provides data or services to clients.

Engineering parallel

A shared subsystem providing a defined service.

Understand

Explain a system

Do not change anything yet.

Inspect how [feature or system] currently works.

Trace it from input to output and identify:
- the main files involved
- important functions and modules
- external dependencies
- where data enters and decisions are made
- where data leaves
- relevant tests

Explain the architecture in plain technical language.
Call out anything uncertain rather than guessing.
